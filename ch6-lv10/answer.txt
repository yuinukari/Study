問題1（N+1問題）の原因を説明し、SQLを1本に書き換えて解決してください。
原因：最初のSQLで当月の注文をまとめて約80万件取ってきた後、プログラムのループ処理の中で「注文の数だけ（80万回）」1件ずつ members テーブルに検索をかけていること。ラウンドトリップが80万回発生するから、致命的に遅くなる。
修正SQL：最初から JOIN（結合）文を使用し、注文情報と会員情報を1本のSQLでまとめて取得するように書き換える。
SELECT o.id, o.member_id, o.order_date, o.total_amount,
       m.name, m.rank, m.region
FROM orders o
JOIN members m ON o.member_id = m.id
WHERE o.order_date BETWEEN '2026-05-01' AND '2026-05-31'
  AND o.status = '発送済';

問題2のSQLの問題点を4つ以上列挙してください。
o (orders) テーブル：30,000,000件（3千万件）に対するフルテーブルスキャン（type: ALL）が発生している。WHERE 句の期間・ステータス条件に対応するインデックスが存在しないため。また、大量のデータをソートするために一時テーブルの作成（Using temporary）とディスクソート（Using filesort）が走り、深刻な負荷を与えている。
m (members) テーブル：2,000,000件に対するフルテーブルスキャン（type: ALL。主キー（PRIMARY）は定義されているが、前段の orders から流れてくるデータ量が多すぎるためインデックスが機能していない。
oi (order_items) テーブル：90,000,000件（9千万件）に対するフルテーブルスキャン（type: ALL。結合キーである order_id にインデックスがないため、結合のたびに全件を走査。
p (products) テーブル：150,000件に対するフルテーブルスキャン（type: ALL。前段のデータ量が多すぎるため主キーが活用できていない。
c (categories) テーブル：200件のフルスキャン。データ量が少ないため単体での影響は軽微だが、全体として全テーブルがフルスキャンになる最悪の結合連鎖を起こしている。

問題点それぞれに対して改善策（インデックス追加・SQL書き換え等）を提案し、優先順位をつけて説明してください。
1.orders テーブルに期間・ステータスでの絞り込み用インデックスがない。
2.order_items テーブルの結合キー（order_id）にインデックスがない。
3.products テーブルの結合キー（category_id）にインデックスがない。
4.9千万件の巨大な明細テーブルを、集計のために毎回最初から全件結合している。
5.巨大なデータセットに対して COUNT(DISTINCT) を多用しており、メモリとCPUへ過大な負荷をかけている。

優先順位【高】：適切なインデックスの追加
理由： アプリケーションのロジックを大きく変更することなく、データベース側の設定のみでフルスキャンを劇的に削減し、最も即効性のあるリターンを得られるため。
優先順位【中】：アプリケーション側のN+1問題の修正
理由： 80万回発行されていた不要なクエリを1回に集約できるため、ネットワーク負荷とバッチ処理時間を大幅に短縮できる。
優先順位【低】：サマリーテーブルやパーティショニングの導入
理由： 性能面では最も根本的な解決策となるが、テーブル設計の変更や日次集計バッチの新設など実装・テストの影響範囲が広いため。

改善するためのDDL（CREATE INDEX 文）をすべて記述してください。
-- 1. ordersの期間・ステータス検索を爆速にするインデックス
CREATE INDEX idx_orders_date_status ON orders (order_date, status, member_id);

-- 2. order_itemsの結合を高速化し、不要なテーブルアクセスを防ぐ複合インデックス
CREATE INDEX idx_order_items_order_id ON order_items (order_id, product_id, quantity, unit_price);

-- 3. productsのカテゴリ結合を最適化するインデックス
CREATE INDEX idx_products_category ON products (category_id, id);

インデックス追加後、EXPLAIN の各テーブルの type 列がどのように変わるかを予測してください。
o (orders)： ALL ➡ range （1ヶ月分のデータのみを範囲走査）
m (members)： ALL ➡ eq_ref （主キーによる1件ずつのピンポイント結合）
oi (order_items)： ALL ➡ ref （注文IDに紐づく数件の明細のみをインデックスで瞬時に取得）
p (products)： ALL ➡ eq_ref （商品の主キーによる1件ずつの等価結合）
c (categories)： ALL ➡ eq_ref （カテゴリの主キーによる1件ずつの等価結合）

インデックス以外のアプローチ（サマリーテーブル・パーティショニング・キャッシュ等）で改善できる点があれば説明してください。
データ規模が非常に巨大（明細9千万件）であるため、長期的にはインデックスだけに頼らず、以下のアーキテクチャ最適化が極めて有効。サマリーテーブル（集計用テーブル）の導入夜間に一括で9千万件を計算するのではなく、毎晩「日次売上集計テーブル」にデータを少しずつ集計・蓄積しておく。
月次レポート出力時は、その計算済みのサマリーデータ（数万件程度）を読み込むだけにすることで、30分以上かかっていた処理を数秒〜数秒にまで短縮可能。パーティショニングの導入orders や order_items を order_date の「月別」でパーティション分割して保存。
これにより、5月の集計を行う際は5月のデータが入った領域（パーティション）のみを走査対象とし、それ以外の過去数年分の数千万件のデータを完全にスキップできるため、ディスクI/Oが劇的に軽くなる。
